### Cadence d’insertion

| Source | Contrôle | Défaut |
|---|---|---|
| BLE live | `scanner.sample_interval` — throttle in-memory par adresse dans `GoveeScanner.on_advertisement` | **60 s** (`DEFAULTS` / `config.example.toml`) |
| HA T&H | `ha_th.sample_interval` | 60 s |
| GATT / CSV / federation ingest | résolution minute typique ; `INSERT OR IGNORE` (ou overwrite) | pas de throttle `sample_interval` |

Chemin BLE : `scanner.py` → `_store` → `Database.upsert_reading`.  
Backfill : `insert_gatt_readings`.

Volume théorique live ≈ `N_devices × 86400 / sample_interval` lignes/jour (ex. 10 capteurs @ 60 s → ~14 400/jour).

|---|---|---|
| `Database.prune` | `db.py` | `DELETE FROM readings WHERE ts < cutoff` |

**Non — pas de**

### Analyse volume par âge — idées SQL

S’appuyer sur l’index `(address, ts)` :

```sql
-- Buckets d'âge relatifs (ex. 0–7, 7–30, 30–90, 90+ jours)
SELECT
  CASE
    WHEN ts >= strftime('%s','now') - 7*86400 THEN '0-7d'
    WHEN ts >= strftime('%s','now') - 30*86400 THEN '7-30d'
    WHEN ts >= strftime('%s','now') - 90*86400 THEN '30-90d'
    ELSE '90d+'
  END AS age_bucket,
  COUNT(*) AS n,
  COUNT(*) * 120 AS bytes_est
FROM readings
GROUP BY age_bucket;

-- Ou par mois civil (proche de device_source_series)
SELECT strftime('%Y-%m', ts, 'unixepoch') AS ym, COUNT(*)
FROM readings GROUP BY ym ORDER BY ym;
```

Pour l’UI : étendre `/api/system` (ou un sous-endpoint) avec ces agrégats + réutiliser l’estimation ~120 B/row déjà dans `list_devices`. Un vrai downsampling de rétention demanderait une table agrégée + job de purge des raw hors fenêtre chaude — **rien de tout ça n’existe encore**.
