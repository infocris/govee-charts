est-ce qu'il eiste des modèles physique simples qui permettent de déterminer dans le cas où 2 volumes communiquent de connaitre l'évolution de la température ?

## Assistant

Oui. Le modèle le plus simple et utile est un **échange thermique linéaire** entre deux volumes (équivalent RC thermique).

## Deux volumes couplés

Pour des pièces \(A\) et \(B\) à températures \(T_A\), \(T_B\) :

\[
C_A \dot{T}_A = -K_{AB}(T_A - T_B) + P_A
\]
\[
C_B \dot{T}_B = -K_{AB}(T_B - T_A) + P_B
\]

- \(C\) : capacité thermique (masse × chaleur spécifique, ou volume × densité × \(c_p\))
- \(K_{AB}\) : conductance thermique (murs, porte ouverte, convection)
- \(P\) : apports (chauffage, soleil, pertes vers l’extérieur)

Sans sources (\(P=0\)), la différence se referme en exponentielle :

\[
\Delta T(t) = \Delta T(0)\, e^{-t/\tau}
\quad\text{avec}\quad
\tau = \frac{C_A C_B}{K_{AB}(C_A+C_B)}
\]

et les deux températures convergent vers la moyenne pondérée par les capacités :

\[
T_\infty = \frac{C_A T_A(0) + C_B T_B(0)}{C_A + C_B}
\]

## Avec l’extérieur

Souvent on ajoute une fuite vers \(T_\text{ext}\) :

\[
C_A \dot{T}_A = -K_{AB}(T_A-T_B) - K_{A,\text{ext}}(T_A-T_\text{ext}) + P_A
\]

C’est le même esprit que votre projection actuelle `sensor = weather + offset`, mais avec une **dynamique** au lieu d’un décalage constant.

## Variantes simples

| Modèle | Idée | Quand l’utiliser |
|--------|------|------------------|
| **RC 1 nœud** | une pièce ↔ extérieur | tendance d’une pièce seule |
| **RC 2 nœuds** | 2 pièces couplées | porte ouverte, couloir ↔ chambre |
| **Mélange d’air** | débit volumique \(Q\) : \(K \approx \rho c_p Q\) | aération, porte grande ouverte |
| **Offset + τ** | \(T_\text{int}(t) = T_\text{ext}(t) + \Delta + \text{filtre}\) | forecast UI, peu de paramètres |

Pour des capteurs Govee, un modèle **très pragmatique** est :

\[
\dot{T}_\text{int} = -\frac{1}{\tau}\bigl(T_\text{int} - (T_\text{ext} + \Delta)\bigr)
\]

où \(\tau\) (souvent 30 min–quelques heures) et \(\Delta\) (biais intérieur) se calibrent sur l’historique.

## Assistant

Voici le process tel qu’il est codé aujourd’hui (après **reboot machine** ou **restart** du service).

## 1. systemd (démarrage / crash)

Unit `govee-charts.service` :

| Étape | Délai |
|--------|--------|
| Attente dépendances | `After=network-online.target bluetooth.target` |
| Si le process quitte | **3 s** (`RestartSec=3`) puis relance (`Restart=always`) |
| Arrêt max | **30 s** (`TimeoutStopSec=30`) |

Donc au boot : Bluetooth → démarrage du service ; si échec immédiat, nouvel essai toutes les **3 s**.

## 2. Scanner BLE (reconnexion réelle à BlueZ)

Boucle dans `_run_adapter` — échec de `scanner.start()` :

### a) BlueZ `InProgress` (très fréquent juste après reboot)

| Tentative | Attente avant retry |
|-----------|---------------------|
| 1 | **15 s** |
| 2 | **30 s** |
| 3 | **45 s** |
| 4 | **60 s** |
| 5 | **75 s** |
| 6 | **90 s** |
| 7 | **105 s** |
| ≥ 8 | **120 s** (plafond) |

Formule : `min(120, 15 × n)` avec `n` = nombre d’échecs `InProgress` consécutifs. Compteur remis à 0 dès qu’un `start()` réussit.

### b) Non autorisé (surtout macOS)

| Tentative | Attente |
|-----------|---------|
| 1 | **30 s** |
| 2 | **60 s** |
| … | `min(300, 30 × n)` |
| ≥ 10 | **300 s** (5 min) |

### c) Autre erreur

Attente fixe **10 s**, puis retry (compteurs auth / InProgress remis à 0).

### d) Après un scan OK puis redémarrage volontaire

- Pause **2 s** entre stop et nouveau start (settle BlueZ).
- Stop avec `InProgress` : **1 retry après 2 s**, puis on ignore.

### e) Linux (votre cas) — surveillance “silencieuse”

- `stale_restart` : **off** (0)
- `recycle` périodique : **off** (0)

(Sur macOS : stale à 120 s sans pub, recycle à 1800 s.)

## 3. UI « Restart » (bouton)

| Étape | Délai |
|--------|--------|
| Attente avant kill process | **0,6 s** |
| Poll santé API | toutes les **1 s**, timeout **45 s** |
| Puis systemd | **3 s** avant relance (voir §1) |

est-ce qu'on peut utiliser une passerelle bluetooth branché sur tuya comme d'un répéteur ?

## Assistant

Non — pas comme un vrai répéteur BLE pour govee-charts.

**Ce que fait une passerelle Bluetooth Tuya**  
Elle est un **pont** vers le cloud / l’app Tuya (Smart Life) : elle parle surtout aux appareils **compatibles Tuya**, puis envoie les données en Wi‑Fi. Elle **ne rebroadcast pas** les publicités BLE Govee pour qu’un autre scanner (BlueZ / Bleak) les entende plus loin.

**Pourquoi ça ne marche pas ici**  
- Les Govee H5075 / H5179 utilisent des pubs BLE **propriétaires**, pas le protocole Tuya.  
- Même si la passerelle « voit » du BLE, ça n’étend pas la portée pour ton collecteur local ni pour la fédération govee-charts.

**Ce qui joue vraiment le rôle de répéteur chez toi**  
- Un **2ᵉ nœud** govee-charts (autre Pi / machine + adaptateur BLE) qui pousse via `federation`  
- Ou un **proxy BLE** type ESPHome / HA Bluetooth Proxy (utile dans HA, pas un repeater transparent pour ton scanner actuel)

En résumé : passerelle Tuya = écosystème Tuya, pas d’extension de portée pour le scan BLE Govee.
